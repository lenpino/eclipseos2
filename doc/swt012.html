SWT Step 012. Tables

Objective

Implement the o.e.swt.widgets.Table, TableItem and TableColumn classes. The test case SWT012_01 checks the columns, the texts of the cells, the bounds, the header and the lines, the selection (single and multiple), the events, removing, scrolling, the placement of items added before the table has a size and with the redrawing off, and the images and colors automatically, and then shows a table to be used by hand.

Task notes

The table is the container control of PM in its detail view, as Tree is in its tree view (see step 011 and lessons learned for the way the records are handled in native memory). What is new:

  • A column is a FIELDINFO (32 bytes), allocated with CM_ALLOCDETAILFIELDINFO and put in the container with CM_INSERTDETAILFIELDINFO. Its offStruct points to a slot of the record, where each cell has the pointer to its string (CFA_STRING), so a record has the extra bytes for 32 columns (the id of the item and 32 pointers).
  • The slot belongs to the column: another column that is inserted before does not move the texts. While there are no columns an implicit one shows the text of the items, and the first TableColumn takes its place, as the Windows port does.
  • Every cell of a new record points to an empty string before the record is inserted: the container paints at once and does not accept a null pointer.
  • The container with CCS_EXTENDSEL lets the selection be empty and be several items by program, and a SWT.SINGLE table is kept to one by Table. The other modes of selection cannot be empty (CCS_SINGLESEL) or select by toggling (CCS_MULTIPLESEL).
  • After a resize the container places its records wrongly (they go up by the height it gains): Table asks it to place them again right after the resize, see lessons.
  • The height of the header is the height of the window minus the top of the viewport of the records; the order of the items, for the access by index, is kept in a vector.

The behavior that differs from Windows is in difference 014.
