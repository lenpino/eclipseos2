SWT Step 026. What the dialogs of Eclipse need

Objective

Fix what Eclipse finds when it runs on the port, starting with its dialogs. The test case SWT026_01 (8 automatic checks) checks Label.setImage (null) and a text after an image; its interactive part shows an image and a label whose image was taken away.

Task notes

  • No dialog with a title area opened (2026-11-17): the wizards (New Project) and the external tools logged a NullPointerException in Label.setImage. TitleAreaDialog.showMessage calls setImage (null) on its label when the message has no icon, and the port used the handle of the image without looking whether there was one.
  • The type of a static of PM (SS_TEXT 1, SS_ICON 3, SS_BITMAP 4...) is a value, not a bit of its own. setImage (null) now makes the label a text again (SS_TEXT), and setText replaces the type instead of adding SS_TEXT to it: after an image it made SS_BITMAP | SS_TEXT, which is SS_GROUPBOX. This second check was not seen failing first: the exception stopped the test before it.
  • The views of Eclipse showed gray, also their titles, and parts came and went when a menu closed over them (2026-11-17). A dump of the windows of PM (-Dswt.watchdog.dump) showed why: the ViewForm of a view is a sibling placed over its CTabFolder, and no control had WS_CLIPSIBLINGS (commented out in Control.widgetStyle since the first version; Windows sets it). On PM a window without it paints over the siblings above it, so each repaint of the folder (at startup, when maximized, when a menu closed) painted gray over the view. Every control has WS_CLIPSIBLINGS now. Composite also set it while painting, but after WinBeginPaint, when the clipping is already made. New test SWT026_02 (7 checks, it read red over the green sibling before the fix); all the automatic tests from SWT010_01 to SWT026_01 still pass.
  • SWT013_01, SWT014_01, SWT015_01, SWT016_01, SWT018_01, SWT020_01 and SWT023_02, which use labels, still pass.
