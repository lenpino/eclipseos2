  • SWT006: changed the behavior of filled versions of some graphic primitives in GC, to be compatible with Windows (and conform to SWT specs). Now graphic primitives use the convention where points that define a primitive are placed between actual (screen) pixels, not inside them. So, when a filled figure is drawn it affects all pixels that are inside the area defined by figure's coordinates. When an outlined figure is drawn it touches pixels to the left and to the bottom from every point that defines the figure's shape. This, in particular, means that given the same width and height a filled rectangle will be 1 pixel smaller in dimensions than an outlined one -- the former will occupy exactly the given number of pixels in width and height while the latter will occupy width + 1 and height + 1 pixels respectively.

2026-11-08

[lpino]

  • New SWT Step 010 (tool bars): o.e.swt.widgets.ToolBar and ToolItem, with the SWT010_01 test case (ant.cmd swt010_01). They do not use the eCS etoolbar control, see difference 012 for the reasons. The latest eCo Software toolkit (2024) was compared with the installed one: its etoolbar.h only adds the TBS_2D style and esplitter.h is identical.
  • Fixed the placement of a single line Text. With a border (the PM entry field with ES_MARGIN) PM moves it by 3 pixels and makes it 6 larger each time it is positioned, and only setBounds() compensated for it, so setSize() and setLocation() misplaced it and repeated calls made it drift. Without a border, the compensation of setBounds() was wrong and made every plain text 6 pixels smaller and moved. It is now done in the internal setBounds(), once, and only for a single line text with a border. Test case SWT009_17.
  • Fixed the VM abort on every empty string (Text/Button/Label.setText("")): a PSZ is never a one-element array any more, see the notes on ASCIIZ strings.
  • Fixed Text.setText() of a multi line text, which inserted the string at the cursor instead of replacing the text. Test case SWT009_14.
  • Menu.setVisible(true) of a pop up menu was an empty method (the Windows code was commented out), so nothing was shown. It now uses WinPopupMenu(), at the pointer or at the location set with setLocation(). PM puts the lower left corner of the menu at the given point while SWT wants the upper left one, and the size of the menu is known only after it has been shown. To avoid seeing it at the wrong place for an instant (which happened from time to time) the menu is first shown below the screen, then moved: its upper left corner goes to the point, or its lower left one if it does not fit below, and it is kept inside the screen. getVisible() still returns false for a pop up menu. Test case SWT009_15.
  • Fixed the direction of the y axis in Control.toDisplay(), toControl() and Display.getCursorLocation() / setCursorLocation(): PM grows upwards from the lower left corner and SWT downwards, and the PM value was passed through. A pop up menu placed with toDisplay() appeared at the bottom of the screen. Besides, getCursorLocation() asked for the text cursor (WinQueryCursorInfo()) and returned null: it uses the new native OS.WinQueryPointerPos() now (the DLL has to be rebuilt). Test case SWT009_16.
  • Fixed 24 constants of OS of the container control (CCS_*, CV_* and CA_*): they were written as decimal numbers though the value is hexadecimal (CV_TREE = 40 instead of 0x40, CCS_READONLY = 20 instead of 0x20, ...). They were found by comparing the 953 constants that OS.java shares with the toolkit headers (pmstddlg.h, pmwin.h, pmgpi.h, pmdev.h): the other 929 are right. Note that a static final int is copied into the classes that use it when they are compiled, so those classes (Tree) have to be recompiled after changing a constant.
  • Found why new Tree() aborted the VM: structs.c asked for the field "cDelta " (a space at the end) of CNRINFO, which does not exist, and the JVM does not check a null jfieldID. OS.MPFROM2SHORT() was also wrong for negative values. Test case SWT009_18. See lessons learned, which also records the audits (tools/audit-constants.py, tools/audit-jni-fields.py) and what was read in the blog of the port.
  • New SWT Step 011 (trees): o.e.swt.widgets.Tree and TreeItem on the container control of PM, written again because the old classes were almost all commented Windows code and the way they handled the records (copies in Java objects) cannot work. The records are handled through their addresses. Test cases SWT011_01 (66 automatic checks and an interactive part) and the old SWT009_11, which had never run on this machine. The container keeps one selected item and cannot have several or none, see difference 013. 19 constants of the container were added to OS.
  • The container did not place its records again when it changed of size, so a tree whose items were added before it had a size looked empty (the items were on top of each other and then out of the visible part). Tree asks it to reposition them after every resize. Seen in the interactive part of SWT011_01, which the automatic checks did not cover; they do now.
  • First look at SWT011_01 on the screen: the tree works with real clicks. Fixed: the images were not drawn (the container needs CA_DRAWBITMAP to draw bitmaps, and its icon cell is 32x32: it is 16x16 now and the rows are 16 pixels high instead of 32), and a click sent the Selection event twice. The tree repositions its records less often after a resize.
  • The container keeps the pointer to the structure of CM_SETCNRINFO: Tree builds it in memory of its own and frees it with the tree. And Tree.setRedraw() hides the container while the redrawing is off, because it paints each record as it is inserted whatever the updating state is (the tree that is filled while visible was drawn twice, the second time with the images). Checked: the same placement with the redrawing off as with it on; seen on the screen: to be confirmed. SWT011_01 has 74 checks.
  • New SWT Step 013 (directory dialog): DirectoryDialog, made of SWT widgets because PM has no dialog to choose a directory: a tree of drives and directories read when they are expanded, with OK and Cancel. Test case SWT013_01 (31 automatic checks, driven from inside the dialog's event loop). Not seen on the screen yet. See difference 015.
  • New SWT Step 012 (tables): Table, TableItem and TableColumn on the container control in its detail view. Test case SWT012_01 (124 automatic checks and an interactive part). First seen on the screen: it showed two defects that were fixed (the second click gave an event without an item, and 300 items took seconds to be added because of the refresh of each record, now once for all of them). Up to 32 columns, one implicit column while there are none, the selection can be empty or multiple (unlike the tree), and the records have to be placed again after each resize, with a message that is not the one of the tree. See difference 014 and lessons learned. 19 constants of the columns (CFA_*) were added to OS.
  • Scrollable.widgetStyle() adds SBS_VERT to any control with a vertical scroll bar; in the container that bit is CCS_EXTENDSEL, which Tree removes.
  • SWT010_01: the arrow of the drop down item opens a pop up menu under the button, the usual way to use it. The SWT.Selection event with detail == SWT.ARROW of a ToolItem gives, in x and y, the lower left corner of the arrow in the coordinates of the tool bar (y grows downwards), where the upper left corner of the menu goes.
