SWT Step 011. Trees

Objective

Implement the o.e.swt.widgets.Tree and TreeItem classes. The test case SWT011_01 checks the hierarchy, the indexes, the texts, the expansion, the bounds, the selection, the events, dispose() and removeAll(), the images and the colors automatically, and then shows a tree to be used by hand. SWT009_11 is the old visual test.

Task notes

The tree is the container control of PM (WC_CONTAINER, class #37) in its tree view, as the Workplace Shell uses it. The records of the container live in native memory and have pointers, so the previous approach, to copy them into Java objects (RECORDCORE) and send the copy, did not work: it released Java arrays with pointers that did not come from them and the VM aborted. Now:

  • A record is handled through its address (TreeItem.handle) with OS.malloc(), OS.free(), OS.memset() and OS.objcpy() with byte[], through Tree.peek() and poke(); CM_INSERTRECORD gets the address of the record that CM_ALLOCRECORD returned and of a RECORDINSERT built in memory.
  • The container keeps pointers to the texts of a record, so each text is allocated apart (the same one for the four views of the record) and freed when it is replaced and when the item is disposed.
  • The id of a TreeItem is stored in the extra bytes of its record (CM_ALLOCRECORD with 4), to find the item from a record when a notification arrives.
  • The events come as WM_CONTROL: CN_EMPHASIS is Selection, CN_ENTER is DefaultSelection, CN_EXPANDTREE and CN_COLLAPSETREE are Expand and Collapse. The container does not send them for what the program does, and a flag avoids it when the container does.

Three problems that were found on the way and are not tree specific are in lessons learned: 24 constants of OS.java written in decimal, "cDelta " in structs.c, and the SBS_VERT that Scrollable adds. The behavior that differs from Windows is in difference 013.
