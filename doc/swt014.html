SWT Step 014. Tracker

Objective

Implement the o.e.swt.widgets.Tracker class: rubber band rectangles, drawn on a composite or on the screen, that the user moves or resizes with the mouse or the keys. The test case SWT014_01 posts to the queue the keys and the mouse messages that the user would send and then calls open(), whose loop reads them (72 automatic checks); then it shows boxes to drag and buttons that move and resize them by hand.

Task notes

The class is the one of Windows with the calls to the system changed. WinTrackRect was not used: it tracks one rectangle and sends no message while it moves it, and SWT needs several rectangles and a Move or Resize event for each step.

  • open() runs a loop of its own with WinGetMsg. The mouse messages and WM_CHAR are read and not dispatched while the tracker works; the rest (paint, timers) are dispatched. A WM_QUIT cancels the tracker and is posted again for the loop of the application.
  • Windows creates a transparent window that covers the screen to get the mouse over the desktop. PM sends all the mouse messages to the window that has the capture of the pointer, wherever the pointer is: the tracker takes it with the parent (or the hidden window of the Display) and releases it at the end. If a control has it already (the tracker is opened from a MouseDown), it is left there, and that control gets the release of the button.
  • The position comes from the message (mp1 mapped from its window to the desktop), not from the pointer, so that posted messages work too. As everywhere, the y axis is turned: SWT grows downwards and PM upwards.
  • The rectangles are drawn by inverting four bands with GpiBitBlt and ROP_DSTINVERT; stippled, 3 pixels wide with PATSYM_HALFTONE, the colors CLR_TRUE and CLR_FALSE and ROP_PATINVERT. Drawing twice restores the screen. The presentation space is the one of the parent (WinGetPS): it covers its children, because SWT composites do not have WS_CLIPCHILDREN, but not the windows that are above it. On the display it is the screen (WinGetScreenPS).
  • When the button is not down, the pointer is put at the middle of the top side (moving) or at the side being resized, as on Windows, and a resize shows the system pointer of that side or corner. Two natives were added for that: WinQuerySysPointer and WinSetPointer, and the constant ROP_PATINVERT.
  • The automatic checks post WM_CHAR, WM_MOUSEMOVE and WM_BUTTON1UP before open(). PM gives the posted messages before the input ones, so the mouse moves that WinSetPointerPos causes come after the tracker has finished; the test empties the queue between checks.
  • The drawing is checked too: a timer of the test (the loop of the tracker dispatches the timers) reads the pixels of the screen with GpiQueryPel while the rectangle is shown. The plain line is inverted whole, corners included; the stippled band is inverted in a checkerboard, half of its pixels; nothing changes inside, and the screen is the same afterwards. On the screen the checkerboard of one pixel looks like a thicker gray line, as on Windows.
  • In the VM with the integration of the mouse the pointer that is seen is the one of the host: PM changes its shape but not its place, so the pointer does not seem to jump to the rectangle when the tracker opens, although WinQueryPointerPos says it did.

The differences with Windows are in difference 016.
