Lessons learned and known problems

What has been found out while porting and testing the widgets on the OS/2 virtual machine (see README-VM.md for the way of working), kept together so that it is not discovered twice. The changes themselves are in what's new, the behavior that differs from Windows in known differences.

The runtime

  • The JVM is IBM Java 1.3.1, build co131-20060605 (SR10), Classic VM, JIT enabled (jitc). -Xint does not exist in it, and -Djava.compiler=NONE (no JIT) does not change the crash of the tree, so the JIT is not the cause.
  • The JNI wrappers abort the VM, with FATAL ERROR in native method: Passed wrong C array to Release<type>ArrayElements, in two situations: when they release an array of one element (an empty PSZ was one, see ASCIIZ strings), and when they release an array with a pointer that was not obtained from it (see the RECORDCORE case below).
  • The JVM does not check the jfieldID it is given: a field name that is not found makes GetFieldID() return NULL and the next GetIntField() ends in General Protection Fault ... EIP = 00000000 and SYS1808, with no Java stack.
  • Posted events (postEvent()) run after a window message has been dispatched, so a loop with nothing to dispatch does not deliver them: a test has to post a message (WM_NULL) first.

Audits that can be repeated

  • tools/audit-constants.py <headers> compares the constants of OS.java with the toolkit headers (pmstddlg.h, pmwin.h, pmgpi.h, pmdev.h, taken from X:\os2tk45\h): 953 are in common and, once the 24 above were fixed, all of them agree. A static final int is copied into the classes that use it when they are compiled, so those have to be recompiled after changing a constant (delete their .class).
  • tools/audit-jni-fields.py checks every GetFieldID() of structs.c against the Java class (305 of them). Six warnings are known and harmless: QMSG.ptl_x/ptl_y are declared on one line, PIB.pib_pchcmd/pib_pchenv are commented out in Java but not in C (a problem only if DosGetInfoBlocks() is used) and TREERECORD has no Java class and is not used.
  • tools/audit-native-types.py compares the type that every native of OS.java returns with the one of its C function. Three functions that return a window were jboolean in C, and Java got the handle cut to one byte plus garbage (step 016). Now there are no differences.

The tree (Tree, SWT009_11, SWT011_01)

It works now (step 011). What had to be found out, in the order it showed up:

  • 24 constants of the container written in decimal, and the "cDelta " of structs.c (above): the first one made CM_SETCNRINFO ask for incompatible views, the second killed the VM on any CNRINFO.
  • OS.objcpy(RECORDCORE, int) copied a record of the container into a Java object with setRECORDCOREFields(), which calls releasePSZBytes() on the strings of the record: it releases Java arrays with pointers that belong to the record, and the JVM aborts with Passed wrong C array. A Java object cannot hold a record that has pointers; the same goes for CM_INSERTRECORD with the Java copy, which needs the record that CM_ALLOCRECORD returned. The tree now handles the records through their addresses (see Tree.java). The marshalling of RECORDCORE and RECORDINSERT in structs.c is still there and still wrong for this use.
  • Scrollable.widgetStyle() adds SBS_VERT, whose value (1) is CCS_EXTENDSEL in the container. That bit was always set whatever the selection style was asked.
  • The container selects the first record that is inserted and from then on always has one selected record, which cannot be deselected (CM_SETRECORDEMPHASIS returns FALSE), and selecting another one replaces it, also by program and with every selection style. The properties of the tree view that differ from Windows are in difference 013.
  • The container does not place its records again when it changes of size. The ones inserted while it had no size (a tree is created without one) are all at the same place, and when it grows they go out of the visible part, moved by the old height: the tree looks empty. Tree sends CM_INVALIDATERECORD with CMA_REPOSITION for all the records (no array and a count of 0) after each WM_SIZE, once the container has taken the new size. It was found by asking for the bounds of the items before and after sizing the tree, not by looking at it: the automatic checks created the tree with its size and the interactive part did not.
  • The container draws icons only, unless CA_DRAWBITMAP is set in the attributes of the container: the images of SWT are bitmaps. And the cell of the icon is 32x32 by default (rows of 32 pixels, a blank square where the image should be): CNRINFO.slBitmapOrIcon with CMA_SLBITMAPORICON sets it, 16x16 gives rows as high as the text (16). An image that is an icon (SWT.ICON) is not drawn this way. This one was reported from the screen: the automatic checks only saw that the bounds of the item grew by the width of the cell.
  • The container keeps the pointer to the structure of CM_SETCNRINFO, it does not copy it. Freeing the block just after the call, or passing a structure of the stack (which is what the marshalling of CNRINFO does), made the records of a container that was resized be placed wrongly (y = -194), while it worked by luck as long as that memory was not reused. Tree builds the structure in memory of the process and frees it when the tree goes. The same marshalling is not safe for CM_QUERYCNRINFO either: the container writes its own string pointer in the structure and the wrapper releases a Java array with it.
  • The container paints each record as it is inserted, even when the updating of its window is disabled (WinEnableWindowUpdate(), what setRedraw(false) does), so a tree that is filled while it is visible shows its items one by one, without the images that are set after. Not asking it to paint (fInvalidateRecord false) is no way out: it then does not measure the records either. Tree hides the window of the container while the redrawing is off and shows it, with the records placed again, when it is on.
  • For one click the container sends more than one CN_EMPHASIS (for the record that gets the selection and for the one that loses it) and also when the plus sign of a record is clicked, which selects that record. Tree keeps the record whose selection it reported and reports only a change.
  • A record that is not shown (inside a collapsed item) is not selected: setSelection() expands the ancestors first.
  • CM_QUERYRECORDEMPHASIS with a record gives the next record with that emphasis, not whether that one has it: the flags of the record (flRecordAttr, at offset 4) are read for that, and the container keeps CRA_EXPANDED and CRA_SELECTED up to date in it.

Seen on the screen (SWT011_01): the tree with its lines, plus and minus signs, text, selection and cursor, the scroll bar, and the events of the real clicks. Not seen yet: the images (after the fix of the attribute that draws them), the Enter key and the scrolling of showItem(). One more thing to review: OS.objcpy(int, int[]) and objcpy(int[], int) copy as many bytes as the array has elements, a quarter of the data; they are not used by the tree.

The table (Table, SWT012_01)

The detail view of the same container (step 012), measured before writing it:

  • With CCS_EXTENDSEL the selection can be empty and be several records by program (the first record that is inserted is selected, and can be deselected, unlike in the tree view); CCS_MULTIPLESEL starts with nothing selected but a click toggles; CCS_SINGLESEL cannot be empty. EXTENDSEL is used for single and multiple selection, and a single selection table is kept to one record by Table.
  • The viewport of the records starts under the titles: the header is 28 pixels in a window of 200 (CM_QUERYVIEWPORTRECT with CMA_WINDOW), and a row is 15 to 18.
  • The cells are pointers to strings in the record and the container paints a record at once when it is inserted: all the pointers have to be valid (an empty string) before CM_INSERTRECORD.
  • When the window grows, the records go up by the height it gains (y becomes -60 for 60 pixels more) and the viewport that the container reports does not follow. What puts them back (tried one by one on a table that was already wrong): the CM_INVALIDATERECORD for all the records with CMA_REPOSITION | CMA_TEXTCHANGED | CMA_ERASE, or sending WM_SIZE again, once the resize is over; scrolling, CM_ARRANGE, hiding and showing, invalidating the window or changing the origin of the workspace do not. Doing it inside the WM_SIZE is too early, and calling the container with WM_SIZE there again makes it worse. Table does it in setBounds() and posts a message to itself from WM_SIZE for the resizes that a layout defers. The lighter CMA_REPOSITION that is enough for the tree view is not enough here.
  • Every CM_INSERTRECORD with invalidation and every CM_INVALIDATERECORD of a record with text costs time in proportion to the number of records: 300 items with text took 5.6 seconds, 400 took 10 (a quadratic growth; with empty cells it was 19 milliseconds). Table inserts without invalidating and refreshes the whole table once, with a message that it posts to itself; the methods that ask for geometry (getBounds(), the top index, the header) do the pending refresh first, because a record that was inserted without it has no place yet. 400 items now take 15 to 35 milliseconds. String.getBytes() was not the cause.
  • In the detail view the container does not draw the image of a record with its text: only a column of its own does, with CFA_BITMAPORICON and the offStruct of hbmBitmap (32). Table puts that column (22 pixels, no title) before the others when the first image is set. Only bitmaps are drawn, not icons (hptrIcon would need another column).
  • The container reports CN_EMPHASIS of a record that is selected before it has marked it, and after clearing the previous one, so asking for the selection at that moment can give nothing: the item of the notification is the one to use (it gave a NullPointerException in the application's listener when the second row was clicked).
  • A field is wider on the screen than its cxWidth: 15 pixels more for the first and 18 for the others with the default font, 12/15 with 8.Helv, 20/24 with 14.Helvetica; the lines do not count, and a hidden container measures the same. Found by reading the separators of a row in the pixels: the bounds of the cells and the click on the titles used the same wrong rule, so a check that compared them passed. Table measures the margins in a hidden container (2026-11-13).
  • CM_INVALIDATERECORD with CMA_REPOSITION moves the horizontal scroll (to 0, or elsewhere when several are pending); the scroll is read before and given back after.
  • CM_SCROLLWINDOW with CMA_VERTICAL and a positive amount shows the records that are lower, in the detail view and in the tree view alike. Tree.showItem() sent the opposite sign and never scrolled down; its checks only looked at the expansion. Both are now checked on the screen (2026-11-13).
  • The titles of the detail view are a child window (CID_LEFTCOLTITLEWND, as wide as the container) that does not scroll: it paints the titles from the left of the viewport. A click on it is not notified; its WM_BUTTON1CLICK goes through the queue of the thread, where Display sees it.
  • Java: the initializers of the fields run after the constructor of the superclass, which creates the container, so the fields that createHandle() uses are set in createWidget() before calling the superclass.

The directory dialog (DirectoryDialog, SWT013_01)

  • PM has no dialog to choose a directory: WinFileDlg chooses files. The dialog is made of widgets (a modal Shell, a Tree, two buttons), see step 013. A directory is shown with a placeholder child until it is expanded: it gives the plus sign without reading the disk, and reading a floppy drive would stop the program.
  • The tree keeps one item selected, so a missing filter path selects the deepest directory that exists (or the first drive), not nothing.
  • Testing a modal dialog: the dialog's loop never returns to the test, so the checks run in an asyncExec task that looks the shell up with display.getShells(), reads its widgets, presses the buttons with notifyListeners(SWT.Selection, ...) and closes the window if something fails. The dialogs of the automatic checks flashed on the screen. A window placed out of the screen is not hidden: PM moves it to the top left corner (tried with -5000, -5000). What worked is not showing it: the system property swt.dialog.invisible=true makes open() skip shell.open() and run the loop all the same; the test sets it only during the automatic part.
  • Drawing the pictures of the tree (a folder and a drive) with GC on an Image: the image has to be filled with the background color first (the border of a new image is not the color of the tree), and the images are disposed when the dialog closes. Without any image the container still reserves the 16x16 cell, and the focus rectangle of the selected item shows as an empty frame.
  • TreeItem has no getItem(int) in this version, only getItems().

The tracker, the cursors and the mouse (SWT014_01 to SWT016_01)

  • Driving a modal loop of the system without a user: the messages that the user would send (WM_CHAR, WM_MOUSEMOVE, WM_BUTTON1UP) are posted before Tracker.open(), and its loop reads them. The posted messages come before the input ones, so the mouse moves caused by WinSetPointerPos arrive after the tracker has ended. The queue is emptied between checks, and a timerExec closes the tracker if the messages were not enough, so that a failure does not hang the test.
  • The position of a mouse message is taken from the message (mp1 mapped to the desktop), not from the pointer or from WinQueryMsgPos(): then a posted or sent message works like a real one.
  • What is on the screen can be checked: a timer runs inside the modal loop (the loop dispatches WM_TIMER) and reads the pixels with GpiQueryPel while the rectangles are shown, before and after. That told that the stippled band is drawn (a checkerboard of one pixel, which the eye takes for a thicker line) and that nothing is left behind. The pointers made by SWT are drawn with WinDrawPointer into an image and read back in the same way.
  • The pointer that a control sets is read with WinQueryPointer after sending it a WM_MOUSEMOVE (WinSendMsg, which runs at once).
  • The timer of the display that sends MouseExit looks at the real pointer: with the window hidden it sends Exit in the middle of a sequence of checks whenever the VM is slow. For those checks the window is shown and the pointer is put over the control with WinSetPointerPos before each message; the control that has the capture counts as having the pointer, which is how MouseHover is checked with the window hidden.
  • A check that prints what it got finds the cause sooner: the first failure of SWT016_01 said only that nothing came (the events were waiting for a message), and the next ones printed the handles that showed the native cut to one byte.
  • The automatic checks that put the pointer (SWT016_01, SWT018_01) fail if the mouse of the host is moved over the window of the VM meanwhile: the integration puts the pointer back where the mouse is. The tests say so before, and a failure says where the pointer is.
  • In the VM with the integration of the mouse the pointer that is seen is the one of the host: WinSetPointerPos moves the pointer of PM (WinQueryPointerPos says so) but not the one on the screen, which only changes its shape. The tracker seems not to jump to the rectangle; without the integration (Host+I in VirtualBox) it does.

The cool bar and the tabs (SWT020_01, SWT018_01)

  • Code of Eclipse that is compiled as it is tests the port well. The emulated CoolBar uses only the public API, and through it six defects of the port came out that no test had seen: setVisible(false) before the shell is open, the border of the composites, two shadow colors, the clipping of the children, the size of a drop down Combo and the minimum of a ToolItem with an image (step 020).
  • Each defect seen on the screen got a check first, and the check was seen to fail before the fix: 182 dark pixels of text before a redraw and 0 after, a combo 122 pixels high for a field of 20, black under a combo. Then the same check tells that the fix works, and it stays.
  • A check of pixels needs a background that is not the right answer. The first check of the part below a combo passed with the defect: the combo was created on a shell already painted, and the gray left there was the color expected. Opening the window of the combo over a black one made it fail as the screen did.
  • A fix for all the controls of a kind (WS_CLIPCHILDREN for every composite) changes what other tests show, and their interactive parts are not checked by anything. The user found the screen behind the combo of SWT009_04: after such a fix, the report names the older tests that have to be looked at.
  • When PM does not tell something (where the notebook draws its tabs), it can be measured: a diagnostic that prints the pixels, run with several texts and five fonts, gave the rule to a pixel. The test does not use the rule: it finds the tabs on the screen by their pixels and puts the pointer near their edges, so it would catch a wrong rule.
  • The rule of the tabs held with one font and failed with another one: a measure with a single font proves little. The metrics of each font (lEmHeight) were printed next to the measures, and the relation came out of the table.

The tools and the virtual machine

  • One vm.sh that hangs is worth a stop: more sessions on a saturated sshd make it worse. Loops that run several tests with long timeouts left it saturated twice; the batteries are run one test at a time with short timeouts (60 to 100 seconds), after one ver that shows the connection answers.
  • A VM with a new IP hangs vm.sh without any message (the yes/no question about the host key is not answered): the key is accepted once by hand with ssh ... test@<ip> ver. VM_HOST can be set in the environment instead of editing vmenv.sh.
  • Measure before guessing. The 5 seconds of adding 300 items to the table were not String.getBytes() (a guess that was checked and dropped) but the invalidation of each record; variants of the code chosen by a system property (-Dswt.table.mode=N) in one run of each told what mattered, and were taken out afterwards. A temporary probe class (ProbeXxx) goes to the VM and is removed from the VM and from the repository when it has answered.
  • The automatic part of a test must not show its widgets: the window is opened after initComponents(), and a widget that is asked for sizes while it is hidden has its geometry computed all the same.
  • -Dswt.test.time=true in SWT012_01 prints the milliseconds of each check, which is what showed the slow one.
  • tools/vm-pull.sh copies the trunk of the VM over the repository with rsync --delete. The doc folder of the VM was old, and a pull reverted the pages and deleted the new ones, also edits that were not committed. Everything is committed before a pull, and the pages are sent to the VM after they are committed (git ls-files doc | xargs tools/vm-push.sh -f; in zsh a list in a variable is not split into words, so $F does not work).
  • A program started from the SSH session of the VM could not take the focus while no window of the desktop was active (just after starting the VM): WinSetFocus failed. After a run from a console of the VM it could. The cause is not known for sure. A test that needs the focus says SKIPPED when it cannot get it, instead of failing or passing; running it once from a console of the VM is the way out (step 017).
  • The sshd of the VM offers only ssh-rsa keys: the key of a new IP is accepted with -o HostKeyAlgorithms=+ssh-rsa -o StrictHostKeyChecking=accept-new. When the VM does not answer at all (vm.sh ends with 255 and nothing printed), nc -z on port 22 of the known addresses tells whether it moved; on 2026-11-10 it went to another network (172.20.10.11).
  • A diagnostic that prints rows of pixels must not trim() them: the leading blanks are the position. For a while the tabs of a notebook seemed to begin at 0 in the diagnostic and at 11 in the test, and the time went into looking for a difference between the two programs that did not exist (step 018).
  • Automatic checks of positions and sizes did not see what the screen showed at once: erased text, a bar six times too high. A count of the dark pixels of a control after a redraw finds the first; comparing getSize() with computeSize() the second (step 020).
  • On 2026-11-12 the VM dropped from the network several times (no answer to ping) and came back with the same address. A vm-push.sh cut in the middle ends without its line >> Enviados, and the VM keeps the old files: after a drop, dir on the VM and the sizes on the Mac tell whether they arrived. A push that used to take seconds took 160.
  • An old address of the VM can belong to another machine later: on 2026-11-11 port 22 of 192.168.1.87 answered, the session reached the authentication and then hung, and a restart of the sshd of the VM changed nothing. The VM was at .88. arp -a on the Mac shows it by the prefix of the MAC addresses of VirtualBox, 08:00:27.
  • A vm.sh session can stay open after the program it ran has ended (no java left in pstat), and the output is lost. Writing the output to a file of the VM (java ... > t.out 2>&1) and reading it with type in a second call does not depend on it.
  • ant.cmd dll builds the DLL but cannot copy it while a test that uses it is open (SYS0032, and still BUILD SUCCESSFUL): the window of the test has to be closed first. A cd to a folder with spaces inside a vm.sh command fails (SYS0003) and the commands after it run in the wrong folder.
  • The Java of the port can be checked on the Mac before sending it: javac --release 8 with the sources of pm and the common ones of Eclipse 2.0.1 in the source path finds the compile errors while the VM is away.

Things learned about PM

  • The notebook (WC_NOTEBOOK) has no message for the place of a tab. With BKS_TABBEDDIALOG the tabs fit their text, and the width set with BKM_SETDIMENSIONS does not count: the first one begins at half the em height and 5 pixels, each one is as wide as its text (GpiQueryTextBox, top left to top right corner) and one and a half em heights, the first one a pixel more. When they do not fit, the last ones are narrowed. BKM_QUERYPAGEID gives 0 when there is no page (step 018).
  • Without WS_CLIPCHILDREN a window paints over its children, and they are not told to paint again: an invalidated parent erases them. The window of a drop down combo box includes its list, also while the list is closed: its size is not that of what is seen (step 020).
  • WinIsWindowVisible is false while any parent is hidden, so it cannot tell whether a control is shown: a check of it made setVisible(false) do nothing before the shell was opened (step 020). The style bit WS_VISIBLE of the window says it.
  • The origin of PM coordinates (desktop, windows, WinPopupMenu, WinSetWindowPos, the pointer) is the lower left corner, and y grows upwards. SWT and Windows use the upper left corner. A point is height - 1 - y, the top edge of a rectangle is height - (y + cy).
  • A single line Text with a border moves its origin by 3 pixels (left and down) each time it is positioned and gets 6 larger when the size is set. A Text that is asked for 77x26 ends up 83x32 if nothing compensates for it.
  • WinQueryCursorInfo() is the text cursor, the pointer is WinQueryPointerPos(). WinQueryMsgPos() is the pointer when the last message was retrieved.
  • The presentation space of a GC has a default view matrix that turns the y axis (GC.java, where it is created). The Gpi calls that take world coordinates (GpiQueryPel, GpiMove, GpiBox) count y from the top there, but WinDrawPointer and the other calls in device coordinates count it from the bottom. Reading with the second convention what was drawn with the first one turns the picture upside down (step 015).
  • A pointer is a monochrome bitmap of double height: the XOR plane in the lower half, the AND plane in the upper one, rows from the bottom, and the hot spot counted from the bottom. There is no WM_SETCURSOR: the default processing of WM_MOUSEMOVE sets the pointer, and a window that wants another one sets it after that.
  • The SWT events of the mouse are posted (postEvent) and run after the next message that readAndDispatch() dispatches. A test that sends a message (WinSendMsg) does not go through the queue: it has to post something (a WM_NULL) for the events to run. Display.wake() does nothing from the thread of the display.
  • A control of PM reports one action of the user with several notifications (the container: clear, select, cursor). An SWT event that stands for the action is sent once, after the burst: the notifications only schedule a check with asyncExec, which runs when the queue is empty (step 012).
  • PM sends WM_MOUSEMOVE to the window under the pointer when a window changes there, also when the pointer has not moved. What counts the time at rest (hover, tool tips) has to look at the position, not at the message (step 018).
  • A native that has never been called may be wrong. A handle that only shares its last digits with the right one is a value returned with a smaller type (jboolean instead of jint).
  • A message that is posted (WinPostMsg) is read before the input of the mouse and the keyboard: a test can put keys and mouse messages in the queue before a modal loop and the loop reads them as if the user had sent them (step 014).
  • The eCS toolbar control (etoolbar.h) can only append buttons; the 2024 toolkit has the same messages as the installed one and only adds the TBS_2D style. esplitter.h is identical in both. The splitter is a container, not a thin bar: it reports no pointer displacement for a sash. See differences 011 and 012.

The blog of the port

The development of the port is told in os2advocacy.blogspot.com (The OS2Diary), by Leonardo Pino (LeoPino), between 2007 and 2010. This is what was read there (36 posts, the last ones of 2007 not completely):

  • No post describes a bug of the IBM Java 1.3.1 as such. The closest ones: Tales from Java (2007-09-07), the toolkit installer refuses to install on Java 1.3 and 1.3.1 and its files are copied by hand; and Almost there (2010-06-09): The only show stopper is a BUG on the system that prevents the JVM to work properly, I believe the problems lays on the kernel+CPU+Java version I'm using, I keep getting SYS1808 and all sorts of silly exceptions on the Java runtime, the tools worked 2 times out of 10. We also get SYS1808 with the crashes above.
  • Fixing things (2008-07-03): on a branch with another C compiler only the first test case ran, the others freeze the system when the window comes up.
  • Update (2010-04-22): the tree was written and crashes, I'm pretty ignorant on the Container control, a complex beast. Next moves (2009-11-27) had planned the tree and the table next, after a bug with the MLM_QUERYLINECOUNT message in Text.
  • Other things the blog says that are confirmed here: Old errors coming back (2008-04-24) doubts a PM macro used all over the port (MPFROM2SHORT, which really was wrong for negative values); Popups working, sort of (2008-06-18), a bad flag combination in WinPopupMenu; Habemus icons (2009-11-03), WinCreatePointerIndirect ignores mini icons; Fixing more things (2009-10-26), the font code is tweaked to go around PM bugs.
