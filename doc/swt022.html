SWT Step 022. The clipboard

Objective

Implement the clipboard of the package org.eclipse.swt.dnd: Clipboard, Transfer, TransferData, ByteArrayTransfer and TextTransfer, with the API of Eclipse 2.0.1, on the clipboard of PM. It is needed by StyledText (copy and paste) and so by the editors of Eclipse. Drag and drop is not part of the step. The test case SWT022_01 (21 automatic checks) sends texts and bytes to the clipboard and back, also through the text fields of PM; its interactive part copies and pastes with another program.

Task notes

  • The classes of Windows are made on OLE; the ones of PM are new, in Eclipse SWT Drag and Drop/pm. DND.java (the constants and the errors) is taken from the common part of the original distribution. Both builds (the development one of tests/SWT and the one of the jar) compile the two folders, and classes.inc lists the six classes.
  • New natives (swt.c, the DLL is built again): WinSetClipbrdData, WinEmptyClipbrd, WinEnumClipbrdFmts, WinQueryClipbrdFmtInfo, DosAllocSharedMem (without a name; the address comes back in an array), DosFreeMem, WinAddAtom and WinQueryAtomName. The anchor block is Display.internal_get_HAB().
  • The data given to the clipboard by address (CFI_POINTER) must be shared memory that can be given to another process: DosAllocSharedMem with OBJ_GIVEABLE | PAG_COMMIT | PAG_READ | PAG_WRITE. The clipboard owns it once it has taken it and frees it when it is emptied; if it does not take it, the clipboard frees it with DosFreeMem. The first version had OBJ_GIVEABLE as 0x20 (that is PAG_DECOMMIT): the allocation failed with 87 and nothing was set. It is 0x200 (bsememf.h).
  • TextTransfer is CF_TEXT: the text in the code page of the system, ended by a zero, as the other programs of PM read and write it. A registered type (Transfer.registerType()) is an atom of the system atom table, as the formats of PM that are not predefined. The clipboard does not keep the size of data given by address: ByteArrayTransfer puts the count of the bytes (4 bytes) before them.
  • setContents() empties the clipboard and puts the data of every type at once (Windows can give it later, when asked); getContents() takes the first type of the transfer that the clipboard has. Both try to open the clipboard 10 times, every 10 ms, as Windows does, when another program has it.
  • Found by the checks of the text fields: Text.selectAll() selected up to the limit of the text, which is 0 until it is set, so it selected nothing; and a multi line text (an MLE) was sent the message of an entry field. It selects up to the length of the text now, with the message of each.

The behavior that differs from Windows is in difference 023.
