SWT Step 016. Mouse events

Objective

Send the MouseMove, MouseEnter, MouseExit and MouseHover events of Control, which were never sent. The test case SWT016_01 sends mouse messages to the controls and compares the events that come out (25 automatic checks); then it shows two boxes, one inside the other, and a list with their events.

Task notes

  • WM_MOUSEMOVE did not reach Control.WM_MOUSEMOVE(): its case was commented since the import. Now it sends MouseMove when the position changes (PM sends WM_MOUSEMOVE also when a window changes under a pointer that does not move), with the position taken from the message, and then sets the cursor of step 015. PM does not tell which buttons are down in a mouse message: the state of a MouseMove asks WinGetKeyState.
  • Windows has TrackMouseEvent; PM has nothing like it. The Display keeps the control that got the last WM_MOUSEMOVE: when another one gets it, the first gets MouseExit and the second MouseEnter; also between a parent and its child, as on Windows. While the control hooks MouseExit or MouseHover, a timer of 100 ms looks where the pointer is: if it is not over the control (another program, the desktop, a hidden window) the control gets MouseExit; if it rests 400 ms on it, MouseHover, once until it moves again. The control that has the capture keeps the pointer.
  • As on Windows the events are posted, and they run after the next message is dispatched. The test sends its messages (WinSendMsg), so it posts a WM_NULL to have them run.
  • The y of all the mouse events was one more than it should (cy - y instead of cy - 1 - y): the top row of a control gave MouseDown at y 1.
  • Three natives declared jboolean in C returned a window handle: WinWindowFromPoint, WinBeginEnumWindows and WinGetNextWindow. Java got only the lowest byte and the rest of the register, so the handles were garbage: moveAbove() did nothing and setCursor() did not change the pointer at once. Found because the test printed a handle that shared only its last digits with the right one. A script compared the types of all the natives in OS.java and swt.c: WinQueryCursorInfo had the opposite mistake (harmless). See lessons learned.
  • Also fixed: Display.getCursorControl() used the text cursor (WinQueryCursorInfo) instead of the pointer; moveAbove(null) did nothing (it goes to the top); getPreviousSibling() left the enumeration of windows open.

The differences with Windows are in difference 018.
